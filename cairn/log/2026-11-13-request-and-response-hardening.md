# Harden what the client sends and what it accepts

Six fixes from the family audit of 2026-11-13 (OAUTH-04, OAUTH-05, OAUTH-06, OAUTH-07, OAUTH-11, OAUTH-12), plus the residual the bounded-waits-and-date-parsing change left open on the redirect listener.

**Basic credentials (OAUTH-07).** `Oauth20ClientStd` now form-urlencodes the client id and the secret before they become the Basic user and password (RFC 6749 section 2.3.1), through a private `form_urlencode` over `form_urlencoded::byte_serialize` that puts the `~` back. Letters, digits and `*-._~` are untouched, so `:` becomes `%3A`, `%` becomes `%25`, `+` becomes `%2B`, a space becomes `+`, and an id or a secret made of unreserved characters is the same on the wire as before. The first cut used `byte_serialize` as is, which escapes `~` as `%7E`: secrets of that shape exist (Microsoft Entra issues secrets holding `~`), a server that decodes the credentials reads `~` and `%7E` alike, and a server that compares them raw, as many do, would have refused what it accepted until then. Keeping every RFC 3986 unreserved character literal costs the decoding servers nothing. An id or a secret holding a reserved character still changes on the wire, which is the fix, and was not tried against a live provider. Sending the secret twice (Basic from the client, `client_secret` in the params) is documented on the `client_secret` field, not refused.

**Issuer (OAUTH-12).** `Oauth20AuthSuccessParams` carries `iss`, and `Oauth20AuthParams::validate` takes `expected_issuer: Option<&str>`: a code whose response names another issuer fails with `IssuerMismatch`, which carries the issuer named. The comparison is the plain string comparison of RFC 9207 section 2.4, so `https://as.example` and `https://as.example/` differ: the caller passes the issuer as the server metadata spells it. A response naming no issuer passes, since most servers do not send one; a caller whose server advertises `authorization_response_iss_parameter_supported` checks `iss` on the success params itself. Error responses are returned as before, without an issuer check: a first cut stored `iss` on the error params too, which grew the validation error past the size clippy accepts for an error type, for a response that carries no code to protect.

**Redirect listener.** `await_redirect` and `await_redirect_on` take `expected_state: Option<&Oauth20State>`. With a state, a request to the redirect path that echoes another one, or none, gets the `404 Not Found` of any stray connection and the wait goes on, so a forged request no longer consumes the listener. The keys are matched without regard to case and the last `state` wins, as in the response parser. The caller still validates the returned URL.

**Secrets in `Display` (OAUTH-04).** The params of the authorization code exchange, the refresh, the device poll, the revocation and both JWT bearer exchanges lost their `Display` impl, which was their body serializer, and gained `to_body(&self) -> Vec<u8>`. The serializer methods (`to_serializer`, `to_form_url_encoded_serializer`) stay. `Oauth20AccessTokenRequest` no longer derives `Debug` over the HTTP coroutine, whose rendering held the pending request as a byte list: it prints its name only. The client credentials and device authorization params carry no secret and keep `Display`. The third leak the audit named, the request line inside `InvalidRedirectRequest`, left with that variant in the previous change.

**Status (OAUTH-05).** The errors of the access token request, the refresh, the client credentials request, the device authorization, the device poll, both JWT bearer exchanges and the registration gained `Status(u16)`, returned when a non-success response does not carry the OAuth error object, as revocation already did. A 2xx that does not parse stays `ParseHttpResponse`.

**Token response (OAUTH-06).** `token_type` defaults to `Bearer` and `expires_in` is an `Option<u64>` read from a number or a numeric string. Which servers send these shapes was not surveyed; the parser is lenient on those two points only.

**State and verifier (OAUTH-11).** Both types have `from_entropy(&[u8; 32])`, base64url-encoding the caller's bytes into 43 characters, and `TryFrom<&[u8]>` with a rule: one or more VSCHAR for the state (`Oauth20StateError`), 43 to 128 unreserved characters for the verifier (`Oauth20PkceCodeVerifierError`). The state's `Deserialize` and the verifier's `FromStr` go through them, so an empty state and a short verifier are refused where they were accepted. `Oauth20State::new` and `Default` draw from the 66 unreserved characters instead of the 95 VSCHAR ones (32 characters carry about 193 bits instead of about 210). No fallible generator was added: the panic is the recorded choice of 2026-11-09, and `from_entropy` is the fallible path.

Breaks: `validate` and both listener functions take one more argument; `Oauth20AuthSuccessParams` has one more field and `Oauth20AuthParamsValidationError` one more variant; eight error enums have a `Status` variant; six `Display` impls are gone; `expires_in` on the token success params is `Option<u64>`; the verifier's `FromStr::Err` is `Oauth20PkceCodeVerifierError`.

Capabilities moved: `authorization-code-grant` (CSRF state, PKCE and Random characters modified; Issuer validation and Caller-supplied randomness added), `client` (Redirect listener modified, Client authentication added), `coroutines` (Error status without an OAuth body added), `token-lifecycle` (Secret handling modified, Lenient success parsing added).

Verified, each test failing before its fix: `basic_credentials_are_form_encoded` read the base64 of `client:id:se+cr%t`, and `basic_credentials_keep_unreserved_characters` read `%7E` for `~` on the first cut; `params_carrying_a_secret_are_not_display` found `Display` on the six types; `debug_hides_the_request_body` found the code as a byte list in the rendering; the eight `an_error_status_without_oauth_body_returns_its_status` got `ParseHttpResponse`; `a_numeric_string_lifetime_is_accepted` and `a_missing_token_type_defaults_to_bearer` got no token; `a_verifier_shorter_than_43_bytes_is_refused`, `a_verifier_longer_than_128_bytes_is_refused` and `an_empty_state_does_not_deserialize` got a value; `a_255_byte_state_holds_255_unreserved_bytes` and `the_default_state_holds_32_unreserved_bytes` found other characters; `a_response_naming_another_issuer_is_refused` got the code, and `a_request_echoing_another_state_is_skipped` and `a_request_echoing_no_state_is_skipped` got the forged request, on the new signatures before the checks were written. The tests that read a body through `to_string()` now read it through `to_body()`, and the two state generator tests assert the unreserved alphabet. `cargo fmt --check`, `cargo clippy -D warnings` over `--all-features --all-targets`, `--no-default-features`, `--no-default-features --features client` and `--no-default-features --features rustls-ring,jwt-bearer` clean, `cargo build --no-default-features` (no_std) clean, `cargo test --all-features` passed (72 unit, 10 doc), `cargo test --no-default-features` passed (47 unit, 9 doc).
